Byte-level BPE for the tiktoken `gpt2` and `cl100k_base` encodings.

`o200k_base` is not implemented. `r50k_base` and `p50k_base` use the `gpt2` split. They are not separate presets. `from_tiktoken` loads any `.tiktoken` rank file with one of the two splits below.

## Pre-tokenization

Hand-written scanner. Same patterns as tiktoken 0.14.0 (`tiktoken_ext/openai_public.py`), including possessive quantifiers. ` ?` is U+0020, not `\s`.

`gpt2`:

```
'(?:[sdmt]|ll|ve|re)| ?\p{L}++| ?\p{N}++| ?[^\s\p{L}\p{N}]++|\s++$|\s+(?!\S)|\s
```

`cl100k_base`:

```
'(?i:[sdmt]|ll|ve|re)|[^\r\n\p{L}\p{N}]?+\p{L}++|\p{N}{1,3}+| ?[^\s\p{L}\p{N}]++[\r\n]*+|\s++$|\s*[\r\n]|\s+(?!\S)|\s
```

Contraction case-fold for `cl100k_base` is ASCII plus U+017F. `ll` / `ve` / `re` are ASCII case-insensitive only.

`\s++$` consumes a whitespace run that reaches the end of the string. On an internal run of length `r >= 2`, `\s+(?!\S)` matches `r - 1`. For `cl100k_base`, `\s*[\r\n]` matches through the last CR or LF in a run that does not reach the end.

The `[^\r\n\p{L}\p{N}]?+` prefix on `cl100k_base` is possessive. If the prefix is taken and the letter run fails, that alternative fails.

Property tables are generated by `scripts/gen_unicode_tables.py` into `src/unicode.hpp` from Python `regex` (this machine: regex 2026.9.29, Unicode 15.0.0). Flags: bit 0 `\p{L}`, bit 1 `\p{N}`, bit 2 `\s`. Two-stage lookup: `stage1[cp >> 8]` selects a 256-byte block. 135 distinct blocks. `\s` is the 25 code points U+0009, U+000A, U+000B, U+000C, U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000 through U+200A, U+2028, U+2029, U+202F, U+205F, U+3000. PCRE2 is not used. PCRE2 10.42 (Unicode 14) does not classify U+208F, U+209D, U+209E, U+209F as letters.

Input must be valid UTF-8. Overlong sequences, surrogates, and truncated sequences throw `std::invalid_argument`.

## Byte-to-unicode mapping

Used only when reading GPT-2 `vocab.bpe` / `encoder.json`. `.tiktoken` files are raw bytes (base64).

Printable bytes map to the same code point. Printable means `str.isprintable` for bytes 0..255 except space: 33..126, 161..172, 174..255 (188 bytes). The other 68 bytes, in ascending order, map from U+0100 upward. `vocab.bpe` stores tokens in that Unicode form (`Ġ` is U+0120). The first line `#version: 0.2` is skipped. Each merge gets the next id starting at 256. The result is checked for equality against `encoder.json` (ignoring `<|endoftext|>` and `<|startoftext|>`).

Specials are not inserted into the byte vocabulary, so `encode_ordinary` does not treat them as one token. They are in the decode table.

```
gpt2         <|endoftext|>    50256
cl100k_base  <|endoftext|>    100257
cl100k_base  <|fim_prefix|>   100258
cl100k_base  <|fim_middle|>   100259
cl100k_base  <|fim_suffix|>   100260
cl100k_base  <|endofprompt|>  100276
```

gpt2: 50256 mergeable ranks (ids 0..50255) plus one special. `vocab_size()` is 50257. cl100k_base: 100256 mergeable ranks plus the five specials. `vocab_size()` is 100261. `max_token_id()` is 100276 because `<|endofprompt|>` is not contiguous with the mergeable range.

## Merge

Rank of a mergeable token is its id. Lower rank merges first. For every token of length at least 2, every cut where both sides are themselves tokens inserts `(left_id, right_id) -> token_id`. The same pair with the same id is ignored. A conflicting id throws.

Per piece:

1. If the piece bytes are in the vocabulary, emit that id.
2. If the piece is one byte, emit `byte_id[byte]`.
3. If `n <= 128`, scan the remaining adjacent pairs in place and erase the winner with `memmove`. Each merge is O(n). A piece is O(n^2). Threshold: `kSmallPiece` in `src/merge.cpp`.
4. If `n > 128`, doubly linked symbols plus a binary heap of `(rank, index, version)`. Stale heap entries are dropped by a per-node version. Each merge is O(log n). A piece is O(n log n).

Tie-break in both paths: strictly lower rank, then lower start index. `priority_queue` is a max-heap, so the comparator is inverted.

`decode` concatenates token bytes and does not check UTF-8. For valid UTF-8, `decode(encode_ordinary(s)) == s` because the pieces partition `s`.

## Data structures

`Encoding` holds `shared_ptr<const Model>`. Copies share the tables.

| structure | role |
| --- | --- |
| `arena` | contiguous token bytes |
| `ByteMap` | open-addressed bytes to id, 0.5 load, hash 0 means empty (real hashes are forced non-zero) |
| `PairMap` | open-addressed `(left_id, right_id)` to merged id. Key 0 is a valid pair, so emptiness is a separate flag |
| `byte_id[256]` | id of each single byte |
| `dec_off`, `dec_len` | decode slice indexed by token id. Missing ids are `0xFFFFFFFF` |
| `tokens` | mergeable records used to build the pair index and to save a file |
| unicode `stage1` + blocks | property flags, see above |

## Threading

`encode_ordinary_batch` partitions the input span by cumulative bytes. Thread `t` starts at the first string whose start offset is at least `total * t / num_threads`. `std::thread`. No locks on the tables. `num_threads == 0` uses `hardware_concurrency` (or 1 if that is 0). The first exception is rethrown after join.

The Python module releases the GIL around `encode_ordinary`, `encode`, `encode_with_specials`, `encode_ordinary_batch`, and `train`.

## Trainer

Frequency BPE on pieces from the selected split. Byte `b` has id `b`. Merge ids start at 256. `vocab_size` includes the 256 byte tokens. `min_frequency` defaults to 2.

Pair counts are updated incrementally. A lazy max-heap skips stale counts. Overlapping pairs (`aaa`) decrement the pair that the merge destroys. A negative count throws.

Tie-break: higher pair frequency, then smaller left id, then smaller right id.

This is not the OpenAI training pipeline.

## tiktoken compatibility

Ground truth is tiktoken 0.14.0 `encode_ordinary`.

| check | result |
| --- | --- |
| `tests/fixtures/tiktoken.tsv` | 156 strings, both presets. Regenerated by `scripts/gen_fixtures.py` |
| scalars U+0000..U+10FFFF except surrogates, nine contexts | Release test `Tiktoken.FullSweep`. gpt2 sha256 `50cd292994a1c43cdaaeb0308dbc157fc52a5de6f7a4776dc374fd32c4441b6a`. cl100k_base sha256 `f3ca2e1af21688c61b7844e66a82dba8f7f91726ccc63256d9a550a6f55228ff`. n = 10008576 |
| same sweep, code points in `[0, 2048)` | gpt2 `d3f22a56e4742e7df71b7212d39a12aafc7c3f5df166535081fa0a281189576c`. cl100k_base `6e5713ca68c56bd850bcdbebe24325b422495e8274ca144984440b21eb3994fb`. n = 18432. Runs in Debug |

The hash is SHA-256 of, for each scalar and context, a little-endian `uint32` length then each id as a little-endian `uint32`. Contexts, in order: `ch`, space+`ch`, `ch`+space, `ch`+LF, LF+`ch`, `'`+`ch`, `'`+`ch`+`a`, `ch`+`ch`, `a`+`ch`+`1`.

`encode_ordinary` ignores specials. `encode(text, allowed)` emits the allowed specials as one id and throws if any other registered special text occurs. `encode_with_specials` allows every registered special. Search is leftmost, then longest. The built-in gpt2 and cl100k_base specials are not prefixes of each other, so this matches tiktoken on those sets. tiktoken compiles specials as a regex alternation in hash order. That order is not a stable rule when one special is a prefix of another.
